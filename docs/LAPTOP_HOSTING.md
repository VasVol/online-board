# Проверка хостинга с ноутбука

26 октября 2026. Приложение работает на ноутбуке как `pole.service`, данные остаются в `data/board.sqlite`. В интернет публикуется production на порту 3001 через временный HTTPS-туннель Pinggy. Dev-сервер Vite не публикуется. Домен `board.vasilyvolovich.com` и DNS не менялись.

## Открыть и выключить доступ

```bash
online-board-public open    # запустить туннель и открыть текущую внешнюю ссылку
online-board-public status  # показать адрес, если он отвечает
online-board-public stop    # выключить только внешний доступ
```

Команда установлена в `~/.local/bin/online-board-public`; локальный ярлык на верхней панели продолжает открывать `http://127.0.0.1:3001/`. Текущий внешний адрес хранится в `~/.local/state/online-board/public-url`, а не в Git. Проверяйте также `systemctl --user is-active pole-tunnel`: файл адреса после аварийного завершения может быть устаревшим.

У бесплатного Pinggy **60 минут на одно подключение**, при новом подключении адрес меняется. Это средство проверки, не постоянное размещение для регулярных уроков. Если туннель завершился, повторите `online-board-public open`; для досрочного обновления адреса выполните `stop`, затем `open`. При сетевом сбое systemd может перезапустить туннель с новым адресом — ранее отправленная ссылка тогда перестанет работать. Автозапуск при входе не включён.

Ноутбук должен оставаться включённым, подключённым к интернету и не засыпать. Глобальные настройки питания не менялись. Закрытие терминала туннель не выключает: им управляет пользовательский systemd.

При первом открытии Pinggy показывает свою страницу подтверждения посещения. После неё открывается доска. Откройте доску именно через внешний HTTPS-адрес, затем нажмите **«Поделиться»**, чтобы ученику передалась ссылка с ключом этой доски. Ссылка на главную страницу открывает отдельный каталог посетителя.

## Уже созданные доски

У localhost и каждого внешнего hostname разные cookie. Данные не исчезают при смене ссылки, но доступ владельца нужно восстановить:

1. В обычном браузере откройте локальный каталог и нажмите «Сохранить ключ владельца».
2. Откройте новый внешний адрес, нажмите «Восстановить доступ» и выберите этот файл.
3. Ученику передавайте ссылку из «Поделиться», **не файл владельца**.

Данные и резервные копии не переносились сторонним хостингам. Провайдер туннеля завершает HTTPS и передаёт HTTP/WebSocket через зашифрованный SSH-канал к ноутбуку. Это не сквозное шифрование содержимого от браузера до ноутбука без посредника.

## Сеть и результаты проверки

В текущей сети ноутбука прямые запросы к крупным файлам временных доменов зависали после первых килобайт. В GNOME уже был включён пользовательский прокси (`127.0.0.1:10808` SOCKS, `10809` HTTP); настройки прокси не менялись. Внешние браузерные проверки выполнялись через этот действующий SOCKS-прокси. На отдельном сервере WebHOST1 HTTPS/API и полный сжатый JS-файл редактора проверены без этого прокси. Доступ из произвольной сети ученика этим не гарантируется — полезно проверить ссылку с мобильного интернета.

Cloudflare Quick Tunnel пробовали с HTTP/2 и QUIC, в обычном и US-регионе: несмотря на сообщения об успешной регистрации, внешний адрес возвращал 1033/530, а QUIC также обрывался по тайм-ауту. localhost.run отвечал по HTTP/WebSocket, но бесплатное ограничение скорости замедляло холодную загрузку редактора; проверка Secure cookie через него тоже не прошла. Эти туннели остановлены. Активный проверенный вариант — Pinggy.

Выполнен `scripts/check-public-board.mjs --restart-local`: два независимых браузерных контекста, реальные жесты и проверка пикселей Canvas, двусторонняя синхронизация WSS, offline/reconnect, Secure cookie, закрытие обоих клиентов перед перезапуском бэкенда, затем загрузка четырёх штрихов новым гостем без кеша. Запрос к доске без ключа получает 404. Проверка создаёт собственную синтетическую доску и удаляет только её через API владельца.

```bash
# По умолчанию берёт текущий адрес из private state-файла.
BOARD_PROXY=socks5://127.0.0.1:10808 node scripts/check-public-board.mjs --restart-local
# Для другого развернутого экземпляра задайте BOARD_URL=https://...;
# флаг --restart-local допустим только для сервера на этом ноутбуке.
```

Тест использует официальный `X-Pinggy-No-Screen` для автоматизированного клиента; у обычного посетителя остаётся страница подтверждения Pinggy. Результат и скриншоты лежат в игнорируемом `test-results/public-smoke/`, capability-ссылки и owner-cookie не выводятся в отчёт.

## Устройство и повторная установка

- `scripts/install-tunnel.py` устанавливает `pole-tunnel.service`, управляющую команду и `run-tunnel.py`, создаёт отдельный SSH-ключ при его отсутствии. Нужны OpenSSH и Python 3. Покупки, аккаунта Pinggy и передачи личных SSH-ключей не требуется.
- Ключ: `~/.ssh/id_ed25519_pole_tunnel`; host keys: `~/.ssh/known_hosts_pole_tunnel`. Первое подключение использует TOFU (`accept-new`); изменившийся host key отклоняется. Не отключать проверку и не сбрасывать файл автоматически.
- У `pole.service` добавлен drop-in `https-tunnel.conf` с `TRUST_LOCAL_PROXY=1`. Только loopback-прокси может сообщить приложению исходный HTTPS через `X-Forwarded-Proto`; прямые LAN-клиенты не считаются доверенными прокси. HTTP на localhost/LAN и HTTPS с Secure cookie проверяются отдельно.
- JS/CSS/HTML сжимаются только на слое статических файлов. Хешированные `/assets/*` кешируются на год; HTML обновляется, приватные API остаются `no-store` и не сжимаются этим middleware. Это сокращает трафик домашнего подключения и повторную загрузку.
- `pole-tunnel` не перезапускается вместе с бэкендом: рестарт приложения сохраняет адрес текущего туннеля. Остановка внешнего доступа не выключает локальную доску.
- Секреты в URL туннеля редактируются перед записью в журнал. Не включать подробные логи заголовков или WebSocket payload.

```bash
npm ci
npm run build
python3 scripts/install-tunnel.py
systemctl --user restart pole
online-board-public open
```
