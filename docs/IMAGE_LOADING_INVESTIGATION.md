# Задержка изображений после вставки через буфер

Исследование 5 ноября 2026, код приложения `9ec8406e899cf075bc9a78987f4d52493616e549`. Пользователь сообщил о пустой рамке на 1–2 минуты у второго участника; вставивший через Ctrl+V обычно видел изображение сразу.

## Вывод

Подтверждены два фактора: изображение из буфера может быть значительно больше исходного JPEG, а текущий транспорт файлов не ограничивает время ожидания зависшего запроса. При искусственной задержке на 65 секунд воспроизведён описанный симптом. Это подтверждает уязвимость реализации к сетевым задержкам, но не устанавливает причину конкретного сбоя на уроке.

Во время исследования публичный сайт передавал синтетические изображения быстро. Устойчивую естественную задержку в минуту воспроизвести не удалось. Показатели сервера на момент проверки не указывали на нехватку памяти, диска или большую нагрузку; это не измерение нагрузки во время урока.

## Что происходит в коде

1. В `src/canvas/Canvas.tsx` и `src/canvas/scene.ts` описание объекта, включая рамку и ссылку на файл, публикуется через Yjs/WebSocket. Содержимое изображения в этот документ не входит.
2. `src/canvas/files.ts` отдельно отправляет файл через HTTP PUT. Второй участник получает его через HTTP GET. Пока файл не получен и не передан редактору, возможна пустая рамка. Вставивший уже располагает локальным файлом.
3. `src/api.ts` использует `fetch` без `AbortSignal` или другого собственного тайм-аута. Ожидание охватывает также чтение JSON тела ответа. Интервал повторов в `FileBridge` — 3 секунды, но он не отменяет ещё выполняющийся запрос.
4. `FileBridge.upload()` обслуживает очередь последовательно. Флаг `busy` блокирует повторные попытки и следующие отправки до завершения текущей. В `load()` идентификатор добавляется в `loaded` перед запросом и удаляется лишь при ошибке: зависшее скачивание этого файла не повторяется. Другие вызовы `load()` могут скачивать другие файлы, поэтому одно скачивание не обязательно блокирует все остальные.
5. В `Canvas.tsx` индикатор сохранения учитывает ожидающие **отправки**, но не ожидающие **скачивания**. Получатель может видеть «Сохранено» при пустом изображении. Это не подтверждение готовности фотографии у всех участников.
6. Если GET пришёл раньше окончания PUT, сервер закономерно возвращает 404 «Изображение ещё не загружено». После успешного PUT нет отдельного события готовности файла: получатель ждёт очередного опроса. Это объясняет добавочную задержку до нескольких секунд, само по себе не минуту.

## Размер файла при Ctrl+V

В отдельном Chromium с синтетическим изображением 1280×960 выполнены кодирование JPEG, декодирование и помещение PNG в настоящий буфер обмена. Затем изображение вставлено в редактор клавишами Ctrl+V.

| Этап одного публичного теста | Размер, байт |
| --- | ---: |
| Синтетический исходный JPEG | 340 451 |
| PNG, помещённый в буфер | 1 750 592 |
| HTTP PUT с JSON/base64 | 2 334 285 |

Приложение отправляет base64 внутри JSON, что увеличивает объём относительно бинарного файла приблизительно на треть. На публичном GET наблюдалось сжатие `zstd` от Caddy; размер JSON нельзя выдавать за точное количество байтов скачивания по сети. PUT отправлялся без такого сжатия.

Проверка только метаданных сохранённых файлов также обнаружила PNG порядка 1,56–2,04 МБ. Реальные изображения не использовались как тестовые материалы и не экспортировались в репозиторий. Не установлено, какие именно из них соответствуют описанной задержке и каков размер их исходников до копирования.

Отдельный риск: компонент Excalidraw допускает файл до 4 МБ, а слой сохранения доски — около 2 МБ. Увеличившийся после копирования файл может остаться локальным с сообщением об отказе сохранения. Это отдельный сценарий, который не объясняет последующее успешное появление того же файла через минуту.

## Проверки

Использовались два независимых браузерных контекста, настоящий WebSocket без BroadcastChannel и реальный Ctrl+V с PNG в буфере. Локальные проверки работали на 4310/4311 с отдельной временной SQLite. Публичные проверки создавали собственные синтетические доски и скрывали их через owner API после теста. Перезапуск работающего приложения не выполнялся.

- **Публичный сайт, PNG около 446 КБ:** первый PUT занял 264 мс, успешный GET — 311 мс. Первый показ проверенных красных пикселей изображения у обоих клиентов зафиксирован примерно через 3,2 секунды после Ctrl+V; перед этим был GET 404 до завершения PUT.
- **Публичный сайт, JPEG около 340 КБ → PNG около 1,75 МБ:** первый PUT занял 321 мс, успешный GET — 684 мс. Первый показ пикселей у обоих — примерно через 3,3 секунды после Ctrl+V. Это отдельные наблюдения, а не гарантия задержки в любой сети.
- **Отправка задержана на 65 секунд:** у вставившего видны обе картинки, у второго нет ни одной; первый PUT не повторяется, второй начинается только после завершения первого, примерно на 65-й секунде. После снятия задержки обе картинки отображаются примерно на 66-й секунде. У получателя во время ожидания написано «Сохранено».
- **Скачивание одного файла задержано на 65 секунд:** у получателя на 15-й секунде загружен один файл из двух, второй не повторяется до завершения задержанного GET. На 66-й секунде присутствуют оба файла и пиксели изображений. Второй файл может скачаться независимо от первого.
- После сценариев проверены reload, offline/reconnect и новый гостевой контекст без локального кеша. Публичные тесты проверяли настоящие пиксели Canvas, а не только наличие объектов сцены; в дополнительном проходе проверено завершение GET каждого файла у текущего и свежего гостя.

## Чего не удалось установить задним числом

На сервере нет истории длительности запросов файлов, времени получения каждого изображения клиентом и прогресса тела ответа. Таблица `files` не содержит времени завершения загрузки; поле `created` приходит от клиента. По нынешнему наличию файла в SQLite нельзя восстановить задержку урока.

В `DEPLOYMENT.md` уже описаны прежние зависания больших передач по пути ноутбук–VPS. Это повод проверять маршрут, но не доказательство повторения той же причины. Успешная отправка в Telegram проверяет другой путь и другой способ передачи; она не измеряет PUT/GET к этому VPS. Версии о провайдере, VPN, потерях пакетов и маршруте остаются гипотезами. Редкий, неуверенно описанный случай пустой картинки у обоих клиентов отдельно не воспроизведён.

## Предлагаемые изменения

1. Добавить ограничение времени попытки отправки и скачивания, включая тело ответа, отмену и повторы с задержкой. События восстановления сети должны ускорять повтор. Не прерывать исправную передачу большого файла слишком коротким тайм-аутом. Стандартный механизм браузера: [AbortSignal.timeout](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static) и [отмена fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch#canceling_a_request).
2. Сделать независимые очереди файлов с небольшим ограниченным параллелизмом и защитой от повторной отправки/скачивания одного файла. Сбой одного файла не должен останавливать остальные отправки. Сохранить локальную копию и правильный индикатор незавершённого сохранения.
3. Показывать получателю загрузку/ошибку конкретной картинки и возможность повторить. После серверного сохранения файла уведомлять клиентов о готовности, сохраняя периодический повтор как запасной путь.
4. Проверить единые ограничения для Ctrl+V и кнопки загрузки. Для фотографий рассмотреть JPEG/WebP с проверкой читаемости мелкого текста; не перекодировать все изображения без разбора и не менять уже сохранённые материалы.
5. Добавить обезличенные замеры времени PUT/GET, объёма, повторов и исхода попытки. Не логировать содержимое изображений, cookie, ключи досок или полные URL WebSocket.

Транспорт и кодирование в рамках исследования 5 ноября не изменялись. Правило пользователя об обновлении без ожидания закрытия вкладок уточнено в AGENTS.md, README.md и DEPLOYMENT.md; на VPS сохранено `require_idle=false`.

## Исправление кодирования, 6 ноября

По отдельному поручению добавлена [оптимизация новых вставок Ctrl+V](CLIPBOARD_IMAGES.md). Она уменьшает PNG фотографий перед отправкой и обходит повторное кодирование SDK. Исходный JPEG при загрузке кнопкой сохраняется побайтно; восстановить его прежний размер из PNG буфера невозможно в общем случае. Старые файлы не переписываются. Тайм-ауты, очереди и индикатор скачивания из предложений выше требуют отдельной работы.
