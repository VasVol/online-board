HTTPS-сертификат Let’s Encrypt выпущен и автоматически продлевается Caddy. Серверная production-сборка всех 133 файлов `dist/assets` побайтно совпала с локальной проверенной сборкой.

Старые `pole-cloudflare` на ноутбуке и VPS остановлены и disabled; облачный объект туннеля сохранён без использования. Не включайте старые туннели и не возвращайте CNAME без отдельного плана.

Схема: браузер → HTTPS/WSS непосредственно на VPS → Caddy → `127.0.0.1:3001`. Входящие 80/443 обслуживает Caddy; HTTP перенаправляется на HTTPS. Данные сохраняет один Node.js-процесс на VPS; ноутбук для работы сайта не нужен. Приложение и административный API Caddy слушают только loopback. Полный файл 1 823 543 байта также скачан с независимого WebHOST1 и сверен по SHA-256. На ноутбуке прямой `curl` к тому же VPS в отдельных проверках по-прежнему зависал после 16–20 КБ (HTTP/1.1 и HTTP/2), хотя Chromium прошёл полный сценарий. ## Автоматическое обновление из GitHub

Постоянное разрешение пользователя от 27 октября 2026: завершённые изменения тестировать, коммитить, отправлять на GitHub и доводить до обновления VPS. Явный запрет публикации в отдельной задаче имеет приоритет. Подробные инструкции для LLM — в `AGENTS.md`.

### Обязательные проверки

- `.githooks/pre-commit` требует отсутствие незафиксированных в индексе изменений и запускает полный `npm run check`. Тестируется то же дерево, которое попадёт в коммит; обход hook запрещён рабочим порядком.
- `.github/workflows/ci.yml`: push/PR → Node 22 → `npm ci` → Chromium → **Run full check** в job **test**. Включены 17 Node unit/integration, 11 тестов механизма обновления на Python, 10 dev E2E и 3 production E2E, TypeScript и build (числа актуальны для настройки, меняются при добавлении тестов).
- VPS не полагается на локальный hook. Он проверяет публичный API GitHub: текущий SHA `main`, repository ID `1432285563`, workflow ID `396402665`, путь `.github/workflows/ci.yml`, event `push`, успешное завершение последнего run/attempt, успешные job `test` и step `Run full check` именно для этого SHA. Пропущенные/упавшие/отменённые тесты, PR и чужие ветки не допускаются.
- Результат ожидания CI не означает обновление сайта. Проверить поле `revision` и статус updater обязательно. Правила защищённой ветки в GitHub этим установщиком не меняются; обязательный барьер перед VPS реализован на самом сервере.

### Механизм и права

`pole-deploy.timer` запускает root-owned `/usr/local/lib/pole-deploy/pole_deploy.py` через `pole-deploy.service` примерно раз в 5–7 минут после завершения предыдущего запуска. Заданы `OnUnitInactiveSec=5min`, случайная задержка до 30 секунд и стандартное окно точности systemd до минуты; в проверенном журнале интервал составил 6 минут. Конфигурация `/etc/pole/deploy.json` — root-only. Репозиторий публичный, для чтения GitHub токены и SSH-ключи не нужны. Сетевая ошибка/лимит API оставляют прежнюю версию и повторяются следующим запуском; непроверенного fallback нет. Обычно расходуется до 12 запросов/час, при ожидающем обновлении до 48; не запускать частое ручное опрашивание GitHub с VPS.

1. Скачать архив точного SHA с GitHub. `npm ci` и `npm run build` выполняются как непривилегированный `pole-build`, без доступа к рабочей БД, в `/var/cache/pole-build/`.
2. Запустить кандидат на `127.0.0.1:4312` с **новой синтетической БД**. Проверить версию, статику, два настоящих WebSocket-клиента, ack записи, свежего клиента, изображение и запрет чужого доступа. Проверить совпадение структуры SQLite с рабочей БД; смена схемы требует ручной миграции.
3. Сохранить готовый root-owned релиз в `/opt/pole/releases/<SHA>`. Повторно проверить, что `main` не изменился за время сборки.
4. Через приватный Unix socket `/run/pole/control.sock` (0600, не доступен через Caddy) получить короткую блокировку. При `require_idle=true` она выдаётся только после 60 секунд без клиентов; новые WebSocket/изменяющие HTTP-запросы получают 503 и могут повториться. Через 120 секунд блокировка истекает, если updater аварийно завершился. Открытая вкладка доски, даже без движения пера, считается активным клиентом. **Текущая стадия разработки:** пользователь отдельно разрешил перезапуск с открытыми тестовыми вкладками; в `/etc/pole/deploy.json` задано `require_idle=false`, используется приватный `/acquire-now`. Перед началом реальных занятий установить `require_idle=true` (значение по умолчанию), без изменения CI/backup/проверок.
5. Создать согласованный SQLite backup в `/var/backups/pole/pre-deploy-*.sqlite`, проверить `integrity_check`; атомарно переключить `current`, перезапустить `pole`, проверить нужный SHA и **публичные HTTPS/WSS** синтетическим сценарием. Успех записать в `/var/lib/pole-deploy/status.json`.
6. При ошибке вернуть прежний код. Не восстанавливать старую БД автоматически: это уничтожило бы более поздние изменения. Если схема успела измениться, остановить автоматизацию и требовать ручного разбора. Неудачный SHA после отката блокируется. `pending.json` позволяет следующему запуску восстановиться после обрыва процесса переключения.

Сохраняются три последних каталога релизов с SHA плюс активный/предыдущий; исходный снимок переноса с нестандартным именем не удаляется. Backup автоматически не удаляются. При свободном месте менее 2 GiB новое построение запрещается. Бэкапы на этом же VPS защищают от ошибки обновления, но не от потери всего сервера.

`/var/lib/pole/` всегда отделён от кода. Деплой не обновляет Caddy/DNS, не переносит владельцев и не сбрасывает cookie. Инфраструктурный updater не заменяет сам себя из GitHub: root-owned скрипты и systemd units обновляются отдельно после просмотра и проверки.

В unit updater каталог `/var/lib/pole` включён в `ReadWritePaths`: даже соединение SQLite `mode=ro` должно иметь возможность создать служебные `-wal`/`-shm` после закрытия последнего писателя ([документация SQLite](https://sqlite.org/wal.html#read_only_databases)). Сам updater открывает рабочую БД только для чтения и явно закрывает соединения; `pole-build` по-прежнему не может войти в каталог с правами 0700. На VPS проверено, что создаваемые SQLite служебные файлы сохраняют владельца `pole` и права 0600.

### Команды сопровождения

```bash
# Проверить текущую версию и результат последнего обновления
curl -fsS https://board.vasilyvolovich.com/api/health
ssh ovh-vps 'sudo python3 /usr/local/lib/pole-deploy/pole_deploy.py status'
ssh ovh-vps 'systemctl list-timers pole-deploy.timer --no-pager'
ssh ovh-vps 'sudo journalctl -u pole-deploy -n 60 --no-pager'

# Проверить сейчас (все барьеры CI/занятия сохраняются)
ssh ovh-vps 'sudo systemctl start pole-deploy.service'

# Пауза перед миграцией/инфраструктурной работой; затем возобновление
ssh ovh-vps 'sudo python3 /usr/local/lib/pole-deploy/pole_deploy.py pause'
ssh ovh-vps 'sudo python3 /usr/local/lib/pole-deploy/pole_deploy.py resume'

# Повторить заблокированный SHA только после разбора и устранения причины
ssh ovh-vps 'sudo python3 /usr/local/lib/pole-deploy/pole_deploy.py retry'
```

Один updater защищён файловой блокировкой. Если он уже работает, сначала дождаться завершения и повторить управляющую команду. `waiting_for_idle` в режиме занятий означает: нужно закрыть вкладки досок и дождаться следующего запуска; не отключать проверку участников без явного разрешения. В текущем режиме разработки `require_idle=false` ожидания нет. `waiting_for_ci`/`waiting_for_required_test`: смотреть workflow именно нужного SHA. `error`/`preparation_failed`/`blocked_failed_release`: смотреть журнал; сайт продолжает прежнюю версию. `manual_intervention`: схему/миграцию разбирать вручную, не применять `retry` вслепую.

Предпочтительный откат успешного, но нежелательного изменения — `git revert <commit>`, обязательные тесты и push: новая версия пройдёт весь тот же путь. Для аварийного ручного возврата сначала `pause`, проверить отсутствие клиентов, сделать backup, проверить совместимость схемы и использовать путь `previous` из `status.json`. Никогда не копировать старый `.sqlite` поверх рабочей WAL-базы.

### Обновление самого механизма размещения

Изменения `deploy/automation/`/`deploy/server/` сначала проходят локальный и GitHub CI. Сверить diff и нужный SHA. На VPS из каталога проверенного релиза выполнить `sudo bash deploy/automation/install.sh`: он устанавливает только известные infra-файлы, сохраняет конфигурацию и включает timer; приложение не перезапускает. Затем проверить `systemd-analyze verify`, status и журнал. Не запускать команды из непроверенной ветки с root. Если меняется `pole.service`, применить restart отдельно в свободное от занятий время с backup.

Для **первой** установки поверх старого снимка без control socket использовался временный root-only флаг `bootstrap_legacy`: остановка старого процесса (при `require_idle=true` только после минуты без TCP-подключений к 3001), затем тот же backup/переключение/проверки. После первого успешного релиза флаг убрать; обычные обновления всегда используют Unix socket и выбранную в root-конфигурации политику активности.

### Свой поддомен: первоначальная настройка и проблемы на ноутбуке

26 октября 2026 после входа пользователя в правильный аккаунт Cloudflare найдена активная зона `vasilyvolovich.com`. Создан отдельный remotely-managed tunnel `board-vasilyvolovich-laptop`, UUID `a252bf02-0929-4464-ae51-dca8e1f703a6`, и маршрут `board.vasilyvolovich.com` → `http://127.0.0.1:3001` с завершающим правилом `http_status:404`. Cloudflare создал proxied CNAME `board` → `a252bf02-0929-4464-ae51-dca8e1f703a6.cfargotunnel.com`. В панели проверено: существующие CNAME корня и `www` по-прежнему указывают на `precious-brioche-36520b.netlify.app`. NS (`clara.ns.cloudflare.com`, `randy.ns.cloudflare.com`), основной сайт и общие настройки аккаунта не менялись.

**Блокер:** публичный адрес нестабилен: ответы 1033/530 и 502, несмотря на регистрацию соединений и периодический статус Healthy. Один успешный `/api/health` не повторился устойчиво. Браузерный `scripts/check-public-board.mjs` остановился на странице 502 до открытия каталога; совместная работа и сохранение через этот домен **не проверены**. При этом локальный `/api/health` отвечает успешно. Точную причину не установили: сетевой маршрут/VPN — гипотеза, а не доказанный диагноз. Доступность панели Cloudflare по HTTPS не проверяет отдельное соединение Tunnel по TCP/UDP 7844.

Повторная проверка после восстановления обычного unit: `/ready` показывает четыре соединения, публичный `/api/health` возвращает 502, локальный — 200. При этом `cloudflared_tunnel_total_requests=0` и `cloudflared_tunnel_request_errors=0`: в этой попытке запрос не был передан локальному обработчику туннеля. Не объяснять этот конкретный 502 падением приложения и не считать сетевую фильтрацию установленной причиной.

Пробовали HTTP/2 (обычный и US-регионы) и QUIC; QUIC обрывался по тайм-ауту. Диагностическая передача соединения через действующий локальный SOCKS также не дала рабочего туннеля. ## Требования к целевому серверу

Для первых уроков: Linux VPS/VDS, от 1 vCPU, 1–2 ГБ RAM, 20 ГБ диска; сборка выполняется в CI. Это стартовая оценка, не гарантия нагрузки. Нужны root/sudo для однократной установки, постоянный процесс Node.js, локальный диск для SQLite, доступные входящие 80/443 и SSH. На действующем сервере сначала прочитать его AGENTS.md и выяснить, какие сайты уже работают.

Использовать один процесс приложения. Caddy или Nginx завершает TLS и передаёт HTTP и WebSocket на `127.0.0.1:3001`. `PUBLIC_ORIGIN=https://board.vasilyvolovich.com`. Не включать сырые access logs для query WebSocket, содержащего гостевой ключ.

## Последовательность развёртывания

1. Проверить доступы и возможности сервера, существующие сервисы и занятые порты. Установить отдельного непривилегированного пользователя приложения, постоянный systemd-сервис и reverse proxy.
2. Подготовить проверенную сборку точного commit. Хранить код релизов отдельно от SQLite/изображений и секретов.
3. Перед переносом существующих досок сделать согласованный backup локальной SQLite; сохранить ключ владельца. Не копировать один `.sqlite` поверх работающей WAL-базы. Локальную копию не удалять.
4. Добавить **только** DNS-запись поддомена в Cloudflare, проверить её разрешение и выпустить TLS-сертификат. Не объявлять сайт готовым по одному HTTP 200.
5. Проверить доступ гостя, два независимых клиента, WebSocket/reconnect, сохранение после restart и изображение без локального кеша. После перехода на новый hostname владельцу понадобится восстановить ключ через интерфейс.
6. Включить автоматические обновления только после успешного первого размещения и проверенного отката.
