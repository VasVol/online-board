Проверка хостинга: 26 октября 2026 года. Целевой публичный адрес — `board.vasilyvolovich.com`; DNS основного домена находится в Cloudflare. NS основного домена не менять и существующие A/AAAA/MX/TXT-записи не затрагивать.

## Состояние

- На ноутбуке настроен SSH-псевдоним `webhost1-board` с отдельным Ed25519-ключом. Действительные host/port/user/path берите из `~/.ssh/config`, не из переписки. Проверено подключение без пароля и совпадение host key с ключом сервера.
- Выданная учётная запись WebHOST1 — непривилегированный пользователь общего сервера AlmaLinux. В панели для сайтов есть обработчики PHP и «не используется», но нет Node.js и настроек reverse proxy. Node/npm отсутствуют, sudo без пароля недоступен; для пользовательского systemd `Linger=no`.
- Python 3.9.25 доступен по SSH: проверено выполнение кода и импорт SQLite (3.34.1). Это подтверждает возможность консольных скриптов, но не поддержку постоянного Python веб-приложения. В панели нет обработчика Python; штатный запуск ASGI/WebSocket не подтверждён. Переписывание бэкенда с Node.js на Python само по себе не устраняет требования к постоянному процессу и reverse proxy. Отсутствие Node.js в PATH также не доказывает запрета его установки в домашний каталог — требуется подтверждение возможностей тарифа.
- Это не готовый VPS для данного приложения. Стабильное размещение требует VPS/VDS с административным доступом либо настройки провайдером постоянного Node.js-процесса и HTTP/WebSocket reverse proxy на текущем тарифе. Не заменять это непроверенным запуском `nohup` с ноутбука.
- На этот хостинг приложение и данные ещё не переносились. DNS на него не переключён. Наличие SSH само по себе не означает успешное размещение доски.
- Для GitHub используется существующий репозиторий `VasVol/online-board`. Публиковать только код и синтетические тестовые материалы: данные досок, ключи доступа, SSH-ключи и пароли не должны попадать в Git.

## Требования к целевому серверу

Для первых уроков: Linux VPS/VDS, от 1 vCPU, 1–2 ГБ RAM, 20 ГБ диска; сборка выполняется в CI. Это стартовая оценка, не гарантия нагрузки. Нужны root/sudo для однократной установки, постоянный процесс Node.js, локальный диск для SQLite, доступные входящие 80/443 и SSH. На действующем сервере сначала прочитать его AGENTS.md и выяснить, какие сайты уже работают.

Использовать один процесс приложения. Caddy или Nginx завершает TLS и передаёт HTTP и WebSocket на `127.0.0.1:3001`. `PUBLIC_ORIGIN=https://board.vasilyvolovich.com`. Не включать сырые access logs для query WebSocket, содержащего гостевой ключ.

## Последовательность развёртывания

1. Проверить доступы и возможности сервера, существующие сервисы и занятые порты. Установить отдельного непривилегированного пользователя приложения, постоянный systemd-сервис и reverse proxy.
2. Подготовить проверенную сборку точного commit. Хранить код релизов отдельно от SQLite/изображений и секретов.
3. Перед переносом существующих досок сделать согласованный backup локальной SQLite; сохранить ключ владельца. Не копировать один `.sqlite` поверх работающей WAL-базы. Локальную копию не удалять.
4. Добавить **только** DNS-запись поддомена в Cloudflare, проверить её разрешение и выпустить TLS-сертификат. Не объявлять сайт готовым по одному HTTP 200.
5. Проверить доступ гостя, два независимых клиента, WebSocket/reconnect, сохранение после restart и изображение без локального кеша. После перехода на новый hostname владельцу понадобится восстановить ключ через интерфейс.
6. Включить автоматические обновления только после успешного первого размещения и проверенного отката.

## GitHub Actions

Проверка `.github/workflows/ci.yml` запускается при push/PR: установка по lockfile, TypeScript, unit/integration, браузерные сценарии dev и production, рабочая сборка. Локальный pre-commit запускает тот же `npm run check`.

Запрошенная схема автодеплоя: **push в `main` → успешные тесты → релиз точного commit → backup → переключение версии → health/WebSocket-проверка → откат к прежнему коду при ошибке**. PR не должен менять рабочий сервер. Данные лежат вне каталога релиза. После несовместимой миграции БД автоматический откат кода запрещён: миграции оформляются отдельно.

Для CI использовать отдельный deploy-ключ с минимальными правами на сервере, а не личный SSH-ключ ноутбука. Секрет — в GitHub Actions Secrets, публичный host key — зафиксирован; не отключать StrictHostKeyChecking и не принимать свежий ssh-keyscan вслепую на каждом deploy. Не запускать непроверенные PR на self-hosted runner с доступом к данным досок.

Job развёртывания и его секреты подключаются после выбора совместимого сервера. Пока автоматические проверки и автоматическое размещение — разные состояния; не писать, что автодеплой работает, пока новая версия действительно не прошла весь путь до публичного сайта.
